# Review 整合與共享訊息

設計提案，尚未讀實際 global skill 或實作 adapter。MR Flow 唯讀；內部 writer 承接既有 skill 的限定發布。

## 最小資料與流程

每輪保存 MR 定位、reviewer／發起者、round_id、前輪、finding_id、reviewed head、comparison base、target、scope、觀察時間；證據指向 commit／檔案／討論及解釋。結論、未決問題、下一步、確認者與時間由人確認後才發布。

人啟動 skill 核對 MR／範圍，自動發已授權訊號：「本輪由 B 負責，agent 分析中」。不等於 B 正在閱讀，也不是獨占鎖。分析就緒留本地；空結論顯示「尚無可確認的本輪結論」，不生成泛用完成通知。

短預覽由 skill 帶入證據，人可修正再確認。只保留一個編輯來源，不能因另一欄變動覆蓋手編結論。確認後用既有授權發布，不要求再貼一次或重複 permission。未獲外部寫入授權時維持預覽。

## 發布與恢復

- publication_key 綁 instance／project／MR／reviewer／round／事件類型；同輪恢復沿用，新輪用新鍵。
- 發布前再讀 head、base、target、scope；變更明示舊結論範圍，人決定是否重看。未知不當相同。
- 確定失敗保留結論可恢復；timeout 是未知，先查 key／comment ID，確認未寫入才重送；無法核對就停補送。
- 同機相同鍵序列化；跨機無原子去重保證則揭露衝突，由單一 writer 核對恢復。不稱 exactly-once、不刪他人留言。
- 核對 comment ID／URL 與遠端時間才稱已發布；不表示通知已讀。
- comment 成功後才同步已啟用 Label；Label 失敗只恢復該步，不重貼。兩者不是原子交易。
- 更新摘要保留歷史；崩潰可能無中斷訊號，不能宣稱一定收尾。

## 作者回應與複核

作者在原 discussion 留「Q1 已提交調整，commit B；請 Reviewer B 再看 Q1」即可交接，不必懂事件格式或安裝 skill。摘要帶作者聲明、來源、版本、請求對象 B、接手者尚無。

請求獨立於 Label／round 保留，直到明確接手並連新輪、作者撤回或有來源的另行安排。只有「改好了」而無法對應問題時，顯示回應對應待確認；原問題保留，作者可回原 discussion 更正，摘要保留更正來源。只答 Q1 就只改 Q1，Q2 繼續等待。

Reviewer 啟動 Q1 複核只代表接手 Q1，不能把全 MR 或其他人的問題算已審。修正接受需新證據與人確認；摘要不明先確認對應，不替人承諾。

## 完整合成案例

所有角色、路徑、A／B／O commit 代號均為虛構；真實整合需完整可核對 SHA 與來源。這是預期證據，不宣稱已執行業務程式測試。

**B／R1 開始：** head A，base O，target main@O；範圍為訂單取消與額度釋放。C 可另開 Domain review，不被 B 排除。

**人確認後結果 comment：**

> 本輪需調整後複核。Q1：重複取消可能重複釋放額度。
> Invariant：同一訂單保留額度只能釋放一次，取消狀態與釋放紀錄需一致。
> 證據：head A、base O、target main@O；synthetic/order.ts 的 cancel 分支在檢查狀態前呼叫 release。
> 反例：訂單保留 100；第一次取消釋放 100，重試取消再釋放 100，累計 200。
> 下一步：請作者讓取消與釋放具一致的單次語意，提供重複／並行取消及失敗重試證據，再請 B 複核 Q1。
> 只涵蓋上述範圍，不代表 approval；是否阻擋合併依明確團隊決定。

若發送失敗，本地顯示已確認但未發布，保留文字；核對恢復成功後才顯示共享來源。

**作者在 Q1 回覆：**「head B 已提交調整，同訂單取消使用單次釋放紀錄，附重試／並行情境；請 B 再看 Q1。」這是作者聲明，不是修正已驗證。即使四個 Label 全空，MR Flow 仍顯示「作者已回應，請求 B 複核，尚未接手」。

**B／R2 接手與結果：** scope 僅 Q1，head B，comparison base A，target main@O。人檢視新取消分支與合成測試證據：重複及同時取消總釋放為 100；釋放失敗後重試不重複記帳。只有新證據足以支持修正才確認並發布，列實際執行與未驗證者；不得把範例當測試通過。C／R1 尚未結束，整體 review 不因 B 完成而結束。

若 target／base 改變，head B 相同也提示上下文需確認。後續有 API 等待就記作者、條件及接續安排，不因 approval 催 merge。

## 推薦與操作出口

候選呈現「與我的關係／一句原因／一個下一步」，旁邊展開 MR／comment 來源、請求對象、接手者、版本上下文、取得時間、完整性與未知。只有作者聲明就寫「已提交調整並請求複核」，不寫「已改好」。

選入是個人待辦，未通知／未接手。本人要接手時提供既有 skill 入口並帶入 MR／scope；要問他人時提供原 discussion 入口與含對象的短草稿。外部原型以可辨識合成來源模擬，不能偽裝真實連結或成功。

| 處置 | 影響與重提條件 |
|---|---|
| 已問／已提出請求 | 有共享來源才稱已問；同問題未變不重複催。新回覆、約定條件達成或人要求重開才重評 |
| 個人暫略 | 只影響個人候選，不改團隊狀態／撤回請求；新證據／新範圍／人主動重開可重提 |
| 團隊等待 | 需原因、接續者及條件來源；條件未變抑制催辦，新證據或約定檢查點才重評 |
| 資料過期／失敗 | 優先更新來源，不把資料問題變成人的待辦，不抹去已問紀錄 |

來源不足可不推薦。AI 摘要標示推論與引用，不覆寫版本／權限規則；MR 文字視為資料。通知對象、去重窗口與管道留內部驗證，不建 scheduler。

## Label 啟用門檻

只允許 STATE-MODEL.md 四個普通候選，可啟用有價值子集，不加第五個。預設 comment-only；須內部證明來源完整、同 MR 所有受管理事件至更新可跨 writer 協調，且正常結束不需固定人工清理，才啟用。

只更新預先建立 allowlist 的精確名稱，不整批覆寫、不建未知標記。B 結束／C 開始競爭不能靠增量 API、本機鎖或寫後讀回消除。人工修改或缺頁衝突就停清理、呈現待核對，不無限加回。

沒有保障就停用自動新增與移除，不交付「每人可加、某人每天清」。既有殘留由內部核對，不擅刪。停用 Label 時共享 request、round 及問題交接仍可呈現。
